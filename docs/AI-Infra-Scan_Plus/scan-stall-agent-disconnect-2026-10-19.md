# AI 基础设施扫描停滞与 Agent 断联问题记录

记录日期：2026-10-19。状态：现场分析已完成本轮取证，修复与验收待实施。下文时间均为北京时间。

受影响现场使用 v1.1.0 离线部署，交付说明中的源码基线为 `c2c18547cef9276c376f86057a5387b7e61bfa62`。本轮记录基于现场日志和该基线的代码路径，不代表已完成修复或重新发布。

## 问题概述

用户反馈大网段全端口扫描效率低，网段任务在某个 IP 的“正在自动识别端口”处持续显示约五天；单主机全端口扫描则长时间停留在“执行深度扫描”。

取证后区分为以下问题：

| 问题 | 本轮结论 |
| --- | --- |
| 网段任务长期显示执行中 | 两次实际扫描均发生 Web 与 Agent 连接读取超时；Agent 退出后重新启动，原任务未恢复，状态也未在断连时同步结束 |
| 单主机停留在深度扫描 | 核心扫描已结束，155 个截图后处理任务中有 1 个未返回，报告流程等待全部子任务而无法继续 |
| 扫描及进度处理随规模变慢 | 裸 IP 串行执行 nmap；每条事件的状态检查还会重复加载该任务的全部历史消息 |

目标地址和完整任务标识保留在本地原始证据中，仓库记录使用任务 A、B、C 代称。

## Agent 的职责和断联含义

这里的 Agent 是执行 nmap、指纹识别和截图等操作的后台扫描进程。网页发起的 AI 基础设施扫描由 Web 服务把任务交给 Agent，Agent 通过 WebSocket 回传进度和结果。基础扫描不要求配置大模型；命令行 `scan` 可以在本地直接执行，不依赖独立 Agent 服务。

本次“Agent 断联”指 Web 服务与扫描进程的 WebSocket 连接断开。扫描进程到目标主机的 HTTP/TCP 连接是另一条链路。

容器内的入口脚本会重新拉起退出的 Agent 子进程，因此容器可以一直处于运行状态，Docker 的 `RestartCount` 仍为 0。当前 Agent 容器的健康检查检测 API Checker，不能据此确认 Go Agent 的扫描任务仍在执行。

## 已确认的代码路径

- [Agent 扫描和后处理](../../common/agent/tasks.go)：核心扫描完成后调用 `analysisWg.Wait()`，等待所有截图后处理任务返回，再计算最终报告。一个子任务未返回就会阻止整份报告继续生成。
- [截图实现](../../common/utils/chromium/screenshot.go)：创建了 30 秒 context，但没有绑定到 browser/page；`ctx.Done()` 分支也没有返回。导航、截图和清理缺少有效的取消边界。
- [上传实现](../../common/utils/api.go)：`UploadFile` 使用没有 `Timeout` 的 HTTP 客户端。
- [Agent 连接处理](../../common/agent/agent.go) 与 [进程入口](../../cmd/agent/main.go)：读取 WebSocket 出错后退出接收流程，主程序停止并结束；[容器入口脚本](../../scripts/start_agent_container.sh) 随后重新启动 Agent，旧内存任务没有恢复流程。
- [Web 连接清理](../../common/websocket/agent.go)：移除 Agent 连接时，没有同步结束其关联的执行中任务。
- [事件状态检查](../../common/websocket/task_manager.go) 调用 [GetSession](../../pkg/database/task.go)，后者预加载 `User` 和全部 `Messages`；仅检查状态却重复加载历史消息，累计工作量随事件数量增长。
- Agent 和 [CLI Runner](../../common/runner/runner.go) 的端口发现路径均逐个裸 IPv4 串行调用 nmap，所有端口发现完成后再进入后续扫描；[nmap 调用](../../common/utils/nmap.go) 没有接入任务 context。

## 事件积压与心跳超时的推断

WebSocket 读取流程同步处理业务事件，包括状态检查、数据库存储和 SSE 推送。心跳配置为每 96 秒发送 Ping、Pong 读取期限 120 秒；所用 Gorilla WebSocket 的 Pong 回调也依赖持续读取连接。

任务 A、B 超时前分别接收约 9,552 和 9,593 条业务事件。根据“收到事件”至“开始处理事件”的日志间隔，首 200 条的中位耗时约 1 毫秒，末 200 条分别约 66 和 68 毫秒。这个间隔包含状态查询等前置工作，不等同于数据库查询的独立性能剖析。

事件积压叠加历史消息重复加载，拖延 Pong 读取，是目前与两次现场超时高度吻合的机制。10 月 19 日 11:34:13，Agent 仍记录收到 Ping 并尝试回复 Pong，Web 却在 11:34:37 读取超时。仍需受控复现确认积压与超时的因果关系，不能直接认定为物理网络故障。

SSE 心跳只证明网页订阅连接仍存活。任务 A 在 Agent 超时时仍有 SSE 推送成功记录，因此浏览器订阅断开不是两次故障的共同前提。

## 后续修复边界

用户要求先定位根因，再确定修复方案，并关注报告完整性。后续应满足：

1. 保留全端口能力和一期输入格式支持，通过批处理、调度和减少重复工作改善吞吐。
2. 让 WebSocket 读取与耗时事件处理互不阻塞，状态检查只读取必要字段；复现并验证大量事件下的心跳行为。
3. 明确 Agent 失联后的任务状态、结果保存和恢复规则，防止任务永久保留执行中；重新注册不能直接视为旧任务已恢复。
4. 保留已完成的检测结果和连接错误，分别记录截图证据、上传及可选 AI 分析的完成状态；不得把连接错误或未完成目标计作“未发现漏洞”。
5. 补充子任务与目标 URL 的关联、阶段开始和结束日志，避免继续依赖笼统的“执行深度扫描”定位问题；诊断字段需脱敏。
6. 为具体操作设置可配置的取消和超时边界，并明确重试、补扫及报告合并规则。截图异常不应丢失已有检测结论，报告须准确说明覆盖和证据缺口。
