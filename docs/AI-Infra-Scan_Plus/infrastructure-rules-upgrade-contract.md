# AI 基础设施规则库独立升级契约

契约版本：1.0。日期：2026-10-09。适用程序基线：AI-Infra-Guard v1.1.0，Linux amd64 内网 Docker Compose 部署。

本契约规定三个基础设施规则目录的存放、交付、更新、验收和回滚方式。规则版本独立于程序版本；日常更新规则不重新构建、导入或更换程序镜像，不迁移数据库。

生效条件：完成首次规则目录迁移、Web 挂载调整和更新脚本适配后，按本契约更新。文档交付本身不代表服务器已完成解耦。现有升级包和已交付规则脚本不能直接视为符合新布局。

## 更新范围

允许更新的范围固定为以下三个目录，目录名称及大小写不得改变。

| 目录 | 内容 | 解耦后的宿主机路径 | Web 容器读取路径 |
| --- | --- | --- | --- |
| fingerprints | AI 基础设施指纹 YAML | /opt/aig/rule-data/fingerprints | /app/data/fingerprints |
| vuln | 中文漏洞规则 YAML | /opt/aig/rule-data/vuln | /app/data/vuln |
| vuln_en | 英文漏洞规则 YAML | /opt/aig/rule-data/vuln_en | /app/data/vuln_en |

不在本次规则更新范围内的内容包括 `data/mcp`、`data/eval`、`data/agents`、程序文件、Docker 镜像、Compose 配置、`.env`、数据库、日志、上传文件及 API Checker 数据卷。首次解耦需要调整 Compose 挂载，但日常规则升级不得再改变部署配置。

## 服务器目录约定

```text
/opt/aig/
├── v1.0.0/                                  # 原程序和历史数据，保留回退
├── v1.1.0/                                  # 当前程序部署配置及业务数据
│   ├── docker-compose.intranet.yml
│   ├── docker-compose.upgrade.yml
│   ├── docker-compose.rules.yml              # 首次解耦时新增的挂载配置
│   ├── data/                                # 其他 data 内容仍留在这里
│   ├── db/
│   ├── logs/
│   └── uploads/
├── rule-data/                               # 当前生效的三个规则目录
│   ├── fingerprints/
│   ├── vuln/
│   └── vuln_en/
├── rules/                                   # 上传包归档，不是运行规则库
│   └── 2026.10.09/                           # 北京时间交付日期
│       ├── update-rules-2026.10.09-001.sh
│       └── rules-2026.10.09-001-intranet.tar.gz
├── rule-backups/                            # 每次更新的独立备份和记录
│   └── rules-2026.10.09-001-时间-进程号/
│       ├── original/data/                   # 更新前完整的三个目录
│       ├── merge-report.json                # 合并、冲突、删除记录
│       ├── before-files.json                # 更新前实际文件摘要
│       ├── merged-files.json                # 更新后实际文件摘要
│       ├── official-manifest.json           # 官方快照清单
│       ├── yamlcheck.log                    # 规则格式检查结果
│       └── DEPLOYED.txt                      # 仅成功后写入的部署记录
└── backups/                                 # 程序升级备份，与规则备份分开
```

更新工具可在 `/opt/aig` 下生成隐藏锁文件及临时目录；失败现场保留，临时目录不能当作当前规则库。备份可额外保存失败候选、迁移记录和诊断日志。

`rule-data` 及其三个子目录必须是真实目录，不使用软链接。保留规则文件原有名称和大小写，Linux 上不同大小写路径必须按清单区分；禁止符号链接、硬链接、设备文件及越出目录的路径。候选、运行规则和本次备份应在同一文件系统，便于可靠移动和恢复。

以后程序升级到其他版本时，仍挂载同一个 `/opt/aig/rule-data`。程序回退不自动回退共享规则；若旧程序不兼容当前规则，应另行选择兼容规则备份恢复。

## 程序读取契约

Web 保留现有 `/app/data` 父目录挂载，额外增加三个精确的子目录挂载。新增配置文件约定为 `/opt/aig/v1.1.0/docker-compose.rules.yml`，内容示例如下；仅在规则目录准备好后启用。

```yaml
services:
  webserver:
    volumes:
      - type: bind
        source: /opt/aig/rule-data/fingerprints
        target: /app/data/fingerprints
        bind:
          create_host_path: false
      - type: bind
        source: /opt/aig/rule-data/vuln
        target: /app/data/vuln
        bind:
          create_host_path: false
      - type: bind
        source: /opt/aig/rule-data/vuln_en
        target: /app/data/vuln_en
        bind:
          create_host_path: false
```

三个精确挂载覆盖父目录中的对应路径，其他 `data` 内容继续从版本目录读取。子目录内原有读写功能保持不变；若要改为只读，须同时禁用知识库编辑及网页更新入口，不能只加只读挂载。

挂载配置启用后，所有 Compose 管理命令必须包含该文件，不得只用前两个文件重建 Web。当前版本的管理入口统一为：

```bash
cd /opt/aig/v1.1.0
docker compose -p aig-v110 \
  -f docker-compose.intranet.yml \
  -f docker-compose.upgrade.yml \
  -f docker-compose.rules.yml ps
```

Agent 的基础设施扫描当前通过 Web 知识库接口获取指纹和漏洞规则，不要求额外挂载这三个目录。独立 CLI 的本地文件扫描不自动使用服务器规则库；若需要使用同一库，须另行配置 CLI 的 `--fps`、`--vul` 路径及语言选项。

宿主机替换了直接 bind 挂载的目录后，仅 `docker stop/start` 或 `restart` 不能保证容器重新绑定到新目录。更新工具必须使用全部有效 Compose 配置重建 Web 容器，例如 `up -d --no-deps --force-recreate --pull never webserver`，并核对最终挂载及规则内容；此操作不更换镜像、不重建 Agent、不删除数据卷。

## 首次解耦要求

首次迁移与日常更新分开处理，使用专用迁移脚本，不重新执行程序升级脚本。

1. 确认实际 Web 项目、规则来源、数据库位置和有效 Compose 文件。当前布局按 `/opt/aig/v1.1.0/data` 预期，但必须以容器挂载检查为准。
2. 在无待执行、运行中扫描任务的维护窗口，禁止新任务和知识库写入，停止 Web 后复制并备份当前三个规则目录到独立库；保留文件属性和自定义内容。
3. 校验复制前后逐文件 SHA256 一致，并验证 Web 运行用户权限可读、需要的目录可写。不得用离线包自带规则替代用户当前规则。
4. 新增精确挂载配置，确认 Compose 合并结果，再用全部配置重建 Web，验收挂载、规则读取及历史数据。
5. 成功前不删除原目录；失败恢复原 Compose 挂载和 Web。成功后，版本目录里的原三个目录仅为迁移快照，不再更新，不作为当前规则库使用。

现有规则更新模板只识别整个 `/app/data` 的 bind 来源，并通过停止、启动 Web 更新父目录下的规则。精确子挂载启用后，这种方式会写入被遮蔽的旧目录；必须先适配挂载识别、Web 重建、回滚和验收，再生成符合本契约的新交付。旧交付文件保持不变，不可原地覆盖或重命名冒充新版。

## 规则版本和交付格式

规则版本命名为 `rules-YYYY.MM.DD-NNN`，日期使用北京时间，`NNN` 为当天递增序号，例如 `rules-2026.10.09-001`。程序版本仍为 `v1.1.0`，两者分别记录。

每次升级仅需上传两个配套文件到同一日期目录：

```text
/opt/aig/rules/YYYY.MM.DD/
├── update-<规则版本>.sh
└── <规则版本>-intranet.tar.gz
```

不得单独替换脚本或资源包、混用版本或覆盖历史交付。脚本固定配套资源包 SHA256，并以脚本自身位置定位资源包；不依赖执行命令时的工作目录。

沿用现有交付的两层包结构，外层资源包至少包含：

```text
<规则版本>-intranet.tar.gz
├── rules.tar.gz             # 内层规则快照
├── baselines/*.json         # 合并时用于识别官方文件的历史清单
├── core.py                  # 校验与合并工具
├── yamlcheck                # 离线 Linux amd64 规则校验器
├── LICENSE
└── NOTICE
```

内层规则快照包含 `data/fingerprints`、`data/vuln`、`data/vuln_en` 及 `manifest.json`、`changes.json`、`CHANGELOG.md`、授权文件和校验结果。包内保留 `data/` 前缀只是交付格式；实际运行目录仍是 `/opt/aig/rule-data`，不能解压成 `rule-data/data/fingerprints`。

`manifest.json` 必须记录规则版本、来源仓库和完整提交 SHA、生成时间、完整逐文件路径与 SHA256、文件大小、统计及校验结果。交付记录必须注明兼容的规则布局与程序/校验器版本；契约 1.0 的精确子挂载布局须与旧父挂载布局明确区分。程序版本一致或 YAML 能解析，不等于检测语义兼容，使用了新的规则字段或引擎能力时必须声明最低程序版本并验证。

SHA256 用于发现损坏和错配，不等于可信签名；脚本与资源包须从可信交付渠道取得。保留 Tencent Zhuque Lab 来源说明、LICENSE 和 NOTICE。

## 每次升级的操作入口

以下为完成首次迁移且取得适配本契约的新交付后的标准用法，不用于直接运行现有旧版交付：

```bash
sudo bash /opt/aig/rules/YYYY.MM.DD/update-<规则版本>.sh
```

`YYYY.MM.DD` 与 `<规则版本>` 替换为本次交付值。只上传，不手动解压覆盖运行库。多 Web 实例必须显式选择目标，脚本不能猜测；不得同时升级程序、执行另一次规则更新或通过网页编辑规则。

服务器需有本地 Linux Docker、支持有效配置的 Compose、现存 Agent 镜像及 root 权限。交付包含离线校验器，复用 Agent 镜像里的 Python，不联网安装依赖、不拉取镜像。日常更新会短暂停止 Web，页面和任务提交在维护窗口不可用，不承诺热更新。

## 更新流程及保护规则

更新脚本必须完成以下流程，不能只解压三个目录后返回成功：

1. 核验配套包 SHA256、内层清单、完整文件集合、安全路径、架构、规则格式和兼容性；异常时在替换前退出。
2. 从实际 Web 容器检查三个精确挂载，逐项确认宿主机路径；拒绝只有父挂载、路径不符、软链接或未知布局。确认同项目 Agent 和实际数据库；有待执行或运行中任务时拒绝更新。
3. 对目标规则库加独占锁，生成候选与合并报告。准备期间不修改运行规则；维护期间禁止新任务和知识库写入，停 Web 后再检查任务状态及原规则摘要，防止并发变化。
4. 完整备份三个目录，校验备份清单并确认空间充足；只替换已校验的三个候选目录。不删除 `rule-data` 根目录，不触碰其他业务目录和 Docker 数据卷。
5. 使用全部有效 Compose 配置重建 Web。确认新容器的三个挂载、文件摘要、权限、健康状态及接口规则读取均正确；恢复任务提交入口后，新扫描任务才能使用新版规则。
6. 仅在全部验收通过后写入成功记录；相同官方版本、相同本地规则和相同合并结果重复执行应跳过替换与重建。失败保留非零退出码、诊断和恢复依据。

自定义规则合并遵循以下约定：

| 规则情况 | 处理方式 |
| --- | --- |
| 已确认且未修改的官方规则 | 使用新官方内容 |
| 本地新增或无法确认来源的规则 | 保留并记录 |
| 本地修改与官方同路径更新冲突 | 本地优先，逐项记录冲突 |
| 大小写路径迁移 | 以清单识别并归一；不可安全判定时拒绝更新 |
| 官方删除已确认未修改的规则 | 默认停止，审核后显式授权该版本删除 |
| 本地修改或自定义规则涉及删除 | 不自动删除 |

如果保留的本地规则不满足格式检查，必须停止更新，不得静默丢弃。允许沿用现有 `--allow-official-deletions` 参数，但授权只适用于本次经过审核的删除项，不扩大删除范围。实际生效库可能包含本地修改和自定义规则，因此既要记录官方版本，也要记录合并后的完整摘要。

## 验收与成功记录

每次至少验收以下内容：

- 三个宿主机来源路径和容器目标路径与本契约一致，其他挂载不变。
- 三个实际规则目录逐文件核对成功，YAML 检查失败数为零。
- Web 健康且页面可访问；知识库接口分别可读取指纹、中文漏洞、英文漏洞。
- 同项目 Agent 重新连接；在受控授权目标上验证代表性新增或修改规则可以被新任务读取。
- 历史任务、模型配置、上传文件和其他 data 内容保留；更新脚本不写数据库，服务正常启动可能产生的运行记录另计。

`DEPLOYED.txt` 或配套部署记录必须包含规则版本、成功时间、资源包 SHA256、实际合并摘要、程序镜像、目标项目/容器、三个挂载路径及备份位置。仅下载、归档、打包或上传不能标记为“已部署”。

## 回滚和保留要求

替换失败、重建失败或验收失败时，脚本必须停止 Web，恢复三个旧目录，用同一组 Compose 配置重建 Web 并再次核验挂载与原摘要。恢复受阻时不得启动不完整规则服务，应保留备份、失败候选和诊断，打印需要人工处理的位置。

断电、SIGKILL 等异常不能保证自动回滚。人工恢复必须先停止 Web，依据本次备份把 `original/data` 中的三个目录恢复到 `/opt/aig/rule-data`，再重建 Web 和验收；不能整包覆盖 `/opt/aig/v1.1.0`，不能只启动仍绑定旧目录的容器。

备份和历史交付默认保留，不自动清理；需要清理时另行审核具体版本。不要删除 `/opt/aig/v1.0.0` 或原 API Checker 数据卷来完成规则更新。

## 后续程序升级必须遵守的边界

新版程序必须继续挂载 `/opt/aig/rule-data` 的三个固定目录，并携带有效规则挂载配置。按后续 [系统平台独立升级契约](platform-upgrade-contract.md) 交付的纯平台包及运行镜像不携带这三个目录的规则资源；首次安装和规则更新均使用独立规则交付。程序回退同样必须保留精确挂载配置，并先检查规则兼容性。现有契约更新工具固定支持 v1.1.0，未来平台升级须同时提供支持目标程序版本的规则管理工具，工具适配不代表规则内容更新。

一句话约定：程序放在版本目录，运行规则放在 `rule-data`，上传包放在 `rules/日期`，规则回滚资料放在 `rule-backups`；规则升级不升级程序，也不改变业务数据位置。
