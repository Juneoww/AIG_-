# AI Infra Guard 系统平台独立升级契约

契约版本：1.0。日期：2026-10-10。适用范围：已完成三个基础设施规则目录解耦的 Linux amd64 内网部署。

系统功能升级与基础设施规则更新分开交付、分开执行、分开验收。平台升级只更新程序、运行依赖和必要的部署管理工具，不携带、不替换、不迁移运行规则资源。当前规则始终保存在 `/opt/aig/rule-data`。

本契约定义后续平台交付标准，配套操作见 [系统平台升级操作文档](platform-upgrade-operations.md)。本文不代表已生成符合契约的新平台包或通用升级脚本。已交付 v1.1.0 整包包含规则，旧 `upgrade-to-v1.1.0.sh` 只适用于原 v1.0.0 迁移流程，不能用于下一次平台升级。

## 平台与规则的边界

| 项目 | 系统平台升级 | 独立规则更新 |
| --- | --- | --- |
| 版本 | vX.Y.Z，例如 v1.2.0 | rules-YYYY.MM.DD-NNN |
| 交付内容 | 程序镜像、部署配置模板、管理工具、升级说明 | 三个规则目录及其清单、校验和合并工具 |
| 程序运行目录 | /opt/aig/vX.Y.Z | 不改变 |
| 运行规则目录 | 保持 /opt/aig/rule-data | 只更新其中三个目录 |
| 业务数据 | 一致性备份后继承；数据库迁移需声明 | 不迁移、不由脚本改写 |
| 验收记录 | 平台版本、镜像、规则摘要、数据迁移结果 | 规则版本、实际合并摘要、平台兼容性 |
| 回滚 | 恢复旧程序、配置和兼容的业务数据 | 恢复对应规则备份，不换程序 |

本轮已解耦的规则资源仅指 `fingerprints`、`vuln`、`vuln_en`。MCP、评测集、Agent 数据尚未按此方式解耦，平台升级必须保留其当前运行内容；若某次发布要升级这些内容，须单独列出范围并取得确认，不能借“平台升级”隐含替换。

平台代码可以包含规则解析引擎、内置检测逻辑和规则管理工具，但不能把上述三个外部规则目录当作程序资源打进平台包。

## 服务器存放位置

```text
/opt/aig/
├── v1.0.0/                              # 历史程序和数据
├── v1.1.0/                              # 升级前运行目录，保留
├── v1.2.0/                              # 示例下一版，由新脚本创建
│   ├── docker-compose.intranet.yml      # 新版程序部署配置
│   ├── docker-compose.upgrade.yml       # 本次卷及部署适配配置
│   ├── docker-compose.rules.yml         # 同一共享规则库的精确挂载
│   ├── .env                             # 继承实际环境配置，不放入交付包
│   ├── data/                            # 保留其他 data 内容，不复制三个旧规则快照
│   ├── db/                              # 从旧版一致性复制并按需迁移
│   ├── logs/
│   ├── uploads/
│   └── PLATFORM-DEPLOYED.json            # 成功后写入
├── rule-data/                           # 平台升级禁止改写
│   ├── fingerprints/
│   ├── vuln/
│   └── vuln_en/
├── packages/platform/v1.2.0/             # 示例平台交付接收目录
│   ├── deploy-platform-v1.2.0.sh
│   └── AIG-platform-v1.2.0-linux-amd64.tar.gz
├── rules/YYYY.MM.DD/                     # 独立规则交付接收目录
├── backups/platform-旧版-to-新版-时间/   # 平台升级备份和恢复依据
└── rule-backups/                         # 独立规则备份，不随平台清理
```

`v1.2.0` 为格式示例，不表示该版本已发布。当前活动版本以运行容器的 Compose 标签、镜像 ID 和挂载为准，不通过目录名称大小排序判断。旧版本目录不会被自动删除或移动；新版本目录由升级脚本创建，已存在时拒绝覆盖。

业务数据暂时继续位于各平台版本目录。升级时复制到新版，旧版留作升级前快照；新版运行后产生的数据不自动同步回旧版。API Checker 命名卷不属于 `/opt/aig` 的普通目录，必须单独备份并记录其准确卷名。

## 平台交付包必须包含的内容

每个版本交付两个外部文件：一个一键脚本和一个配套资源包，放在同一目录，不改名、不混用版本。脚本固定资源包 SHA256；可信渠道取得两个文件，摘要校验不能替代来源信任。

资源包的逻辑结构为：

```text
AIG-platform-vX.Y.Z-linux-amd64.tar.gz
├── manifest.json                         # 版本、文件清单、摘要、兼容和迁移要求
├── SHA256SUMS.txt                        # 全部有效负载文件的校验值
├── images/aig-platform-vX.Y.Z-amd64.tar.gz  # Web 和 Agent 离线镜像
├── compose/                             # 配置模板，不包含生产密钥
│   ├── docker-compose.intranet.yml
│   ├── docker-compose.upgrade.yml
│   └── docker-compose.rules.yml
├── tools/                               # 平台升级、验收、回滚及兼容管理工具
├── migrations/                          # 仅在需要时提供数据库迁移程序
├── RELEASE-NOTES.md
├── OPERATIONS.md
├── LICENSE
└── NOTICE
```

禁止包含 `data-*.tar.gz`、`rules-*.tar.gz`、`fingerprints`、`vuln`、`vuln_en` 的规则文件，或任意改名后携带的这些规则快照。也不得携带生产数据库、日志、上传文件、API Key 或现场 `.env`。工具的无害测试样例可以用于隔离验收，不安装成运行规则库、不写入 `/opt/aig/rule-data`。

“不含规则”同时约束镜像：新发布 Web/Agent 运行镜像不能内置这三个目录的规则文件，不能先复制进镜像层后仅在末层删除。打包前必须检查导出镜像的层内容和最终文件系统，确认没有运行规则快照；缺少外部挂载时拒绝启动扫描功能，不回退到镜像内旧规则。

`manifest.json` 至少包含以下信息：

- 交付类型 `platform`、平台版本、源代码完整提交、构建时间和 Linux amd64 架构。
- 契约版本、可直接升级的源平台版本范围，以及不可跨越的迁移步骤。
- 所有有效负载文件的路径、大小、SHA256；Web/Agent 镜像引用及导入后可核验的镜像身份。不得使用可漂移的 `latest`。
- `contains_infrastructure_rules=false`，三个固定规则挂载路径及支持的规则格式/引擎能力。
- 规则管理工具支持的程序版本和布局；兼容性是否已经验证，不能只声明“最低 v1.1.0”。
- 数据库迁移版本、所改表结构、是否可逆、恢复方式；不需要迁移时明确写“无迁移”。
- API Checker 卷继承策略、端口和环境配置变更、依赖与所需磁盘空间估算。

包文件集合必须与清单完全一致，拒绝未知可执行负载、重复路径、越界路径及不允许的链接。旧交付只归档，不原地修改冒充符合新契约。

## 程序和规则兼容性

新版 Web 仍读取 `/app/data/fingerprints`、`/app/data/vuln`、`/app/data/vuln_en`，分别挂载固定宿主路径。`/app/data` 父目录继续指向新版的其他 data 内容。启动、停止、重建和回滚都必须使用完整有效 Compose 配置，包括规则挂载文件。

程序升级不得改变当前规则字节、目录权限和所有权，不修改规则部署版本记录。验收前后对三个目录的路径、逐文件摘要及目录属性进行比较；版本记录可能缺失或包含自定义差异时，用实际摘要作为依据，不把平台版本当规则版本。

发现新版平台不兼容当前规则时，必须在停服前拒绝升级并说明原因。平台脚本不能自动下载、替换、规范化或降级规则；由操作者另行安排规则更新或选择兼容平台版本，并确认中间组合也可运行。不能保证中间组合兼容时，需要单独审批联合维护方案，不属于普通平台一键升级。

当前 `rules-2026.10.10-001` 契约工具固定检查 `/opt/aig/v1.1.0` 和 v1.1.0 镜像标签。升级到其他平台版本前，发布方必须提供兼容目标版本的规则更新工具；不能要求操作者修改旧脚本或关闭版本校验。工具适配可以作为无规则内容的管理程序更新，或另行提供独立规则交付修订，规则内容摘要不因此变化。

## 一键脚本操作接口

未来每个合规平台交付必须实现下列接口。这些是待实现的交付要求，不是旧脚本已有参数：

- `--check`：只读核验版本、挂载、规则兼容、数据库、空间和配套包；不停止服务、不导入镜像、不创建版本目录、不迁移数据。
- 无参数：执行本次平台升级，打印当前/目标版本、关键路径、备份位置、验收结果和退出码。
- `--rollback --backup <本次备份绝对路径>`：针对本次升级恢复，核对备份身份及当前状态，不能猜测卷名或覆盖正在使用的数据。
- `--help`：说明适用源版本、依赖、停机影响、参数和维护要求。

上传接收目录需由上传工具或运维事先建立。资源包无需操作者手动解压；脚本负责校验、安全展开和运行。默认要求 root、本机 Docker/Compose 和已验证维护入口；不联网安装依赖，不拉取镜像，不运行源码构建。

## 平台升级事务

升级脚本必须按以下顺序实施，任一步失败不能写入成功记录：

1. 只读识别唯一实际 Web/Agent、当前镜像、项目、运行目录、全部 Compose 文件、端口、环境配置、业务挂载和命名卷。检查已经使用三个精确子挂载，拒绝未知布局。
2. 校验包、规则与数据库兼容性、依赖、目标路径和空间。导入配套离线镜像后核验身份；此阶段旧服务继续运行，规则不写入。
3. 获取与规则更新共用的规则锁及平台升级锁，遵循同一锁顺序；当前工具使用 `/opt/aig/.aig-rules.lock`、`/opt/aig/.upgrade-v1.1.0.lock`。在统一锁协议迁移前，新工具须兼容这两个锁，不能创建不互斥的新锁替代它们。
4. 建立维护入口，禁止新任务和规则编辑；确认无 todo/doing 任务，停止旧服务并复查。Web、Agent 和 API Checker 相关写入均静止后备份数据库、上传文件、日志、其他 data、全部部署配置及 API Checker 卷；校验备份，记录规则摘要但不复制规则内容进平台包。
5. 创建独立新版运行目录，复制业务数据和实际配置。过滤版本目录中已废弃的三个规则快照，保留其他 data 内容；结合新版模板迁移实际配置，不盲目覆盖现场 `.env`、模型配置、端口或自定义参数。
6. 默认采用独立新版 API Checker 卷，从停止写入的旧卷复制并校验，原卷保留。若该发布必须复用原卷，须在发布清单声明，验证可恢复的完整备份和数据格式兼容，不能静默创建空卷或猜测卷名。
7. 仅对新版数据库副本执行声明的迁移。记录旧/新数据库格式与结果，不在旧数据库上原地迁移。构造目标 Compose，固定新镜像，仍挂载原 `/opt/aig/rule-data`，继承对外端口和内网配置。
8. 确认旧服务已停止、没有同端口双写实例后启动新版 Web/Agent。使用全部有效配置，不拉取、不构建、不删除卷；旧容器名称或全局网络名称存在冲突时按发布方案处理，不能删除其他项目资源。
9. 验收新版功能、Agent/API Checker 健康、知识库、规则摘要和历史业务数据。只对预先授权的受控样例进行验证，不默认触发真实网段或全端口扫描；AI 报告如作为发布门槛须另行声明所需模型配置。
10. 全部通过后恢复访问入口，写平台成功记录。保留旧版本、旧镜像、旧卷和本次备份，不自动清理；平台成功不修改独立规则版本标记。

升级期间发生失败，先停止候选新版，再依据本次备份恢复旧版本的实际挂载和配置。旧服务恢复及验证失败时保留现场，并报告明确的人工恢复路径，不启动空库、不启动两个写入实例。断电和 SIGKILL 不能保证自动恢复，必须保存足够的阶段记录。

## 验收与记录

平台成功记录 `PLATFORM-DEPLOYED.json` 至少记录源/目标平台版本、实际镜像 ID、代码提交、包摘要、旧/新项目、运行目录、完整 Compose 文件、所有业务挂载、旧/新卷、数据库迁移结果、规则版本标记及实际规则摘要、备份位置、验收结果和成功时间。

发布前和服务器执行时均应检查：

- 平台包及运行镜像不含三个规则目录的资源；平台脚本没有规则写入分支。
- 新版三个规则挂载来源仍为 `/opt/aig/rule-data`，升级前后文件、目录属性和实际容器读取内容一致。
- 新版 Web、Agent、API Checker 健康；历史任务、模型配置和上传文件可用。
- 现场端口保留，默认原为 8088 则升级后仍为 8088；不增加公网暴露。
- 数据库迁移经过升级与失败恢复测试，新规则管理工具支持目标程序版本。
- 损坏包、忙碌任务、空间不足、挂载缺失、迁移失败和新版启动失败均有拒绝/回滚测试；已有其他业务容器不受影响。

## 平台回滚边界

平台回滚保持 `/opt/aig/rule-data` 不动，并先检查旧平台能解析当前规则。如果平台升级后另行更新过规则，旧平台不再兼容，平台回滚须拒绝，不能顺带恢复旧规则；规则回滚由独立流程处理。

新版尚未对外开放时，失败自动恢复升级前数据库与卷副本。新版已经产生业务数据后，直接切回旧版快照可能丢失新增任务和上传文件；必须先保存新版数据，再确认可逆迁移或经明确授权恢复旧快照。操作入口不得把数据库文件复制回来冒充无损回滚。

禁止 `down -v`、Docker prune、覆盖共享规则库、直接删除整个 `/opt/aig`、删除历史版本或原卷来完成升级。备份和历史交付的清理属于单独审批操作。

## 当前打包工具需要适配的事项

当前 `scripts/package-intranet.ps1` 会导出整个 `data/`，运行镜像构建也会复制 `data`。未来发布方须先修改平台打包和 Docker 构建流程，排除三个规则资源目录，并实现本契约的升级/回滚接口与测试，才能把新交付标记为“纯平台包”。仅不解压旧包里的规则，不等于平台包已经与规则解耦。

配套 [基础设施规则升级契约](infrastructure-rules-upgrade-contract.md) 同步采用此边界：后续纯平台包不携带这三个默认规则，新装规则也须另行交付；已经保存的历史整包不按新契约重新标记或覆盖。
