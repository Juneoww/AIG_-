# AI Infra Guard 系统平台升级操作文档：v1.1.1 实际交付

更新日期：2026-10-21。本节给出 v1.1.1 的实际接口，配套 [升级契约](platform-upgrade-contract.md)、[修复说明](v1.1.1-release-notes.md) 和 [验证依据](v1.1.1-verification.md)。文末完整保留 2026-10-10 的通用操作原文；其中 v1.2.0 和“未来脚本”均为历史规划示例，实际部署 v1.1.1 请使用本节命令。

## 适用现场和交付边界

仅支持 Linux amd64、运行目录 `/opt/aig/v1.1.0` 的已交付旧 Web/Agent 双容器 v1.1.0，且三个规则目录已经精确挂载自 `/opt/aig/rule-data/{fingerprints,vuln,vuln_en}`。脚本按容器标签、实际挂载、完整 Compose 和固定镜像 ID 识别源部署，未知布局在停服前拒绝；不适用于源码部署、其他架构、前后端拆分布局或 v1.0.0 首次迁移。数据库无迁移。

本版提供两个配套外部文件：`deploy-platform-v1.1.1.sh` 和 `AIG-platform-v1.1.1-linux-amd64.tar.gz`。资源包包含离线 Web/Agent 镜像、三份 Compose 模板、平台及规则兼容管理工具、说明与 LICENSE/NOTICE，不包含三个基础设施规则目录的资源包或镜像内规则快照，也不包含生产数据库、日志、上传文件和现场密钥。平台升级继续使用当前共享规则库，保持规则字节、目录属性和部署记录不变。

源码侧本次输出目录为 `release/v1.1.1-contract-20261021/`，原 `release/v1.1.1/` 历史交付保留。GitHub v1.1.1 的自定义附件仅为上述两个文件。维护工具及模板的交付提交与实际运行镜像的源码提交分别记录为清单中的 `source_commit`、`image_source_commit`；本次重打包不代表重新构建已验证运行镜像。以本次配套文件摘要、包内清单和服务器验收记录为准，不能从目录时间或文件名推断当前运行版本。

## 上传、只读预检和执行

服务器须预先具备 root、Python 3.8+、本机 Docker、Docker Compose v2、GNU cp、iptables/ip6tables 和可用的 DOCKER-USER 链。磁盘空间由本次清单下限及现场数据估算共同校验。脚本不联网安装依赖、不拉取镜像、不在现场构建源码；不支持 rootless/userns、远程卷、IPv6 项目网络或未知业务挂载。

事先建立接收目录 `/opt/aig/packages/platform/v1.1.1/`，通过可信渠道上传这两个文件，不改名、不混用历史脚本和资源包，不必手动解压。不要预先创建目标运行目录 `/opt/aig/v1.1.1`。可以从任意工作目录执行：

```bash
sudo bash /opt/aig/packages/platform/v1.1.1/deploy-platform-v1.1.1.sh --help
sudo bash /opt/aig/packages/platform/v1.1.1/deploy-platform-v1.1.1.sh --check
```

`--check` 校验配套包、兼容性、源部署、规则挂载、任务状态和空间；不停止服务、不导入镜像、不创建运行目录或锁。摘要用于检测损坏与混包，不能代替来源信任。

维护窗口前须在旧页面明确终止旧卡住任务，结束全部 API Checker 检查，并停止人工规则与配置编辑。自动空闲检查只覆盖 SQLite 中的扫描任务；旧 Checker 无实时活动计数接口，脚本不能证明它已空闲。确认没有 todo/doing 任务后执行：

```bash
sudo bash /opt/aig/packages/platform/v1.1.1/deploy-platform-v1.1.1.sh
```

升级会暂时中断页面访问。维护入口阻断外部 Web 访问，保留回环和项目内部探针；停止旧 Web/Agent 后复查数据库，待相关写入静止后备份并校验数据库、上传、日志、其他 data、全部实际配置和准确的 Checker 卷。脚本新建 `/opt/aig/v1.1.1`，继承现场生效的环境、发布端口和网络，复制业务数据并创建独立新版 Checker 卷，保留旧目录、旧容器、旧镜像和旧卷。旧目录中已废弃的三个规则快照不会复制到新版。

## 三份 Compose 和升级验收

包内 `compose/` 必须具有三份 JSON 格式的合法 YAML 模板，安装器会读取并渲染使用：

| 配置文件 | 用途 |
| --- | --- |
| docker-compose.intranet.yml | 固定本版 Web/Agent 程序镜像和容器身份，承接实际服务配置 |
| docker-compose.upgrade.yml | 继承并适配业务 bind、独立新版 Checker 卷 |
| docker-compose.rules.yml | 三个共享规则目录的精确 bind，来源仍为 /opt/aig/rule-data |

模板不能用默认端口、环境或网络覆盖现场有效配置。生成后的三份配置可能包含密钥，仅 root 可读；不要作为公开诊断文件上传。

新版项目为 `aig-v111`，容器为 `ai-infra-guard-webserver-v111` 和 `ai-infra-guard-agent-v111`。状态与日志必须使用完整配置：

```bash
cd /opt/aig/v1.1.1
sudo docker compose -p aig-v111 \
  -f docker-compose.intranet.yml \
  -f docker-compose.upgrade.yml \
  -f docker-compose.rules.yml ps
```

查看日志时只将最后的 `ps` 替换为 `logs --tail 100 webserver agent`。不要在旧目录启动旧版争用端口或写入数据。

脚本验收容器健康、Checker `/healthz`、Web 内存中的实际 Agent 连接状态、三个知识库读取、历史业务数据和规则摘要；验收通过、维护入口恢复后才写入 `/opt/aig/v1.1.1/PLATFORM-DEPLOYED.json`。页面继续使用现场原地址与端口。验收不默认扫描真实目标，不要求 AI 模型配置；不自动续扫、不自动重写旧任务状态。现场是否已更新，以成功回执、成功记录和实际容器身份为准。

## 失败和主动回滚

脚本打印 `/opt/aig/backups/platform-v1.1.0-to-v1.1.1-时间-随机值/`。`STATE.json` 记录阶段、原配置、容器和镜像身份、业务与规则摘要、旧/新/备份 Checker 卷及验收结果。备份含生产配置，应按密钥数据保管。

升级失败时先停止候选，再尝试恢复未修改的原容器并验收。失败目录、候选卷和记录保留；再次执行遇到已存在目标目录会拒绝，须先审核失败现场。成功后的主动回滚接口为：

```bash
sudo bash /opt/aig/packages/platform/v1.1.1/deploy-platform-v1.1.1.sh \
  --rollback --backup /opt/aig/backups/本次打印的实际备份目录
```

回滚先停止新版并保存完整候选目录和 Checker 卷。仅在新版业务数据与升级前精确一致、共享规则仍一致时自动切回原容器。已有新增任务、模型修改、上传、其他 data 或 Checker 写入时，保存现场后拒绝可能丢失数据的恢复，并恢复新版；脚本无跳过此保护的参数，应另行安排数据合并或明确授权的快照恢复。规则已变化时自动回滚也拒绝，平台回滚不回退规则。

断电、SIGKILL 或恢复失败须人工核对 `STATE.json`、`ROLLBACK.json` 和实际容器状态。若 `access_may_be_public=true`，先保留 `accepted_service` 对应的当前写入版本，保存其数据并处理维护策略，不能直接切回旧快照。仅确认候选未开放访问时，才能先停候选、确认无同端口双写，再按记录启动原 Agent/Web。按倒序核对 `maintenance-restore.json` 中本次维护策略的撤销命令，不清空全局防火墙。禁止 `down -v`、Docker prune、删除历史目录、原卷或共享规则库。

## 升级后继续独立规则更新

规则兼容转换器安装到 `/opt/aig/v1.1.1/platform-tools/rules-compatible/prepare_rules_v111.py`。它仅接受固定摘要白名单中的可信原始配套交付 `rules-2026.10.10-002`、`rules-2026.10.19-004`，拒绝未知、修改或混配输入；平台包不携带这两份规则资源包。

在独立规则维护流程中，给转换器传入 `--script 原脚本 --resource 原资源包 --output 不存在的新目录`，得到 v1.1.1 兼容脚本和配套包。它只修改管理代码的路径及平台版本检查，原交付与内层规则逐字保留，转换本身不更新共享规则。实际应用时将生成的两个配套文件一起放在独立规则接收目录，遵循该规则交付的检查、执行和回滚说明。首次解耦已完成，不重复 `--migrate`，不同时运行平台与规则更新。

# AI Infra Guard 系统平台升级操作文档

日期：2026-10-10。面向内网运维，配套 [系统平台独立升级契约](platform-upgrade-contract.md)。

以后只改系统功能时，使用纯平台包；更新指纹或漏洞内容时，使用独立规则包。两个流程不同时执行。平台升级继续使用当前 `/opt/aig/rule-data`，不能重新导入规则。

本文的 `v1.2.0` 是下一版本示例，不是已发布版本。未来 `deploy-platform-*.sh` 的 `--check` 和 `--rollback` 接口尚须按契约实现并随实际发布交付；现在不要把这些参数传给旧 `upgrade-to-v1.1.0.sh`。

## 当前与未来目录

当前程序及业务数据按 `/opt/aig/v1.1.0` 管理，三个独立规则位于 `/opt/aig/rule-data`。当前旧程序和升级备份继续保留。未来平台包上传到 `/opt/aig/packages/platform/<平台版本>/`，脚本创建 `/opt/aig/<平台版本>/`，不要提前创建或覆盖该运行目录。

| 内容 | 位置 | 平台升级如何处理 |
| --- | --- | --- |
| 程序、部署配置及业务数据 | /opt/aig/v1.1.0 等版本目录 | 新建目标版本目录，继承数据和配置 |
| 基础设施运行规则 | /opt/aig/rule-data | 不改内容、版本、权限或路径 |
| 平台交付脚本与资源包 | /opt/aig/packages/platform/版本 | 按版本归档，脚本与包成对保留 |
| 平台一致性备份和恢复记录 | /opt/aig/backups/platform-旧版-to-新版-时间 | 升级脚本创建并核验 |
| 独立规则包 | /opt/aig/rules/日期 | 与平台包分开上传和执行 |
| 独立规则备份 | /opt/aig/rule-backups | 不随平台升级改写或清理 |

API Checker 历史数据位于 Docker 命名卷，平台脚本负责识别、备份并复制到发布方案指定的新卷；不要手动选择一个空卷代替原卷。

## 判断该使用哪种更新

- 新页面、新扫描参数、任务管理改进、漏洞引擎修复、运行依赖升级：平台升级。
- 新 AI 产品指纹、新 CVE 规则、中文/英文漏洞描述或检测内容变更：规则更新。
- 功能要求新的规则格式：发布方先确认兼容关系，分别安排两个交付；不能把规则偷偷打进平台包，也不能盲目先更新任意一方。

若只有平台升级，升级结束后“平台版本”改变，“规则内容及其实际摘要”不变。首次 `--migrate` 仅改变规则存放和挂载方式，不代表已应用某个官方规则版本。

## 接收平台交付

发布方应给你两个文件，以示例下一版为例：

```text
/opt/aig/packages/platform/v1.2.0/
├── deploy-platform-v1.2.0.sh
└── AIG-platform-v1.2.0-linux-amd64.tar.gz
```

通过上传工具建立接收目录，将两个文件一起上传；不改名、不自行解压、不混用旧脚本。发布说明必须明确能否从当前平台直接升级、是否迁移数据库、预计维护时间，以及适配新版的独立规则更新工具如何取得。

当前 `rules-2026.10.10-001` 规则工具只支持 v1.1.0。如果发布方不能提供支持新平台的规则管理工具，该平台交付不满足完整运维要求，不能仅为绕过检查把新版目录改名为 v1.1.0。

## 日常一键升级

确认上传的是实际已发布、符合契约的包，且没有待执行或运行中的任务、其他规则更新或程序升级。服务器需满足该次发布声明的架构、Docker/Compose、维护入口和空间要求。

未来合规交付的标准执行方式如下；将版本替换为本次实际版本：

```bash
sudo bash /opt/aig/packages/platform/v1.2.0/deploy-platform-v1.2.0.sh
```

这一条命令应自动完成预检、镜像导入、维护保护、一致性备份、数据继承、数据库迁移、新版部署、验收和失败恢复。操作者不需要手动移动数据库、改 Compose、删除容器或覆盖规则。过程中页面会暂时不可用，不承诺无停机升级。

如只想先核对条件，未来脚本必须提供可选只读检查：

```bash
sudo bash /opt/aig/packages/platform/v1.2.0/deploy-platform-v1.2.0.sh --check
```

检查失败时按具体原因处理，不关闭规则兼容性、路径、忙碌任务或备份校验。默认无参数升级也必须包含同样的预检，不要求操作者必须先运行两次命令。

## 升级成功后如何确认

以脚本最终成功回执和目标目录的 `PLATFORM-DEPLOYED.json` 为准，不能只看 `docker load` 完成或目录已经创建。若成功，示例新版本位于 `/opt/aig/v1.2.0`，旧目录 `/opt/aig/v1.1.0` 仍保留；实际当前版本以运行容器标签及镜像核对。

页面地址沿用当前部署的对外端口。原来使用 `http://服务器内网IP:8088/` 且本次未明确调整端口，则继续使用该地址。

运维至少确认页面功能、Agent/API Checker 健康、历史任务和模型配置、上传文件以及三类知识库可读。平台脚本应同时核对规则摘要与三个精确挂载没有变化，不能靠手工“看目录存在”验收。

## 后续查看状态和日志

下面是示例新项目 `aig-v120` 的只读管理命令；项目名和全部配置文件必须以本次成功记录及实际容器标签为准，不照抄到其他部署。

```bash
cd /opt/aig/v1.2.0
sudo docker compose -p aig-v120 \
  -f docker-compose.intranet.yml \
  -f docker-compose.upgrade.yml \
  -f docker-compose.rules.yml ps
```

查看最近日志时，使用同一组配置，只把最后的 `ps` 换成 `logs --tail 100 webserver agent`。重建或恢复服务也必须带完整配置；少了 `docker-compose.rules.yml` 可能丢失独立规则挂载。不要回到旧目录启动旧版与新版争用端口或写入数据。

## 平台升级失败或需要回退

升级中失败，由脚本尝试停新版、恢复旧配置和旧数据副本，并验证旧服务。脚本报告恢复失败或维护入口未恢复时，不要反复执行、删除失败目录或手动清空卷；保留控制台输出、工作目录和备份，按回执诊断。

升级完成后主动回退，未来合规脚本的接口为：

```bash
sudo bash /opt/aig/packages/platform/v1.2.0/deploy-platform-v1.2.0.sh \
  --rollback --backup /opt/aig/backups/本次实际备份目录
```

必须填实际备份绝对路径。回退前暂停任务，保存新版已产生的数据，确认数据库可逆迁移或明确接受旧快照恢复的影响。直接恢复升级前快照可能丢失升级后的新增任务、模型修改和上传文件，脚本不得静默执行这种有损恢复。

平台回退不自动回退规则。若规则在平台升级后单独更新过，需先检查旧平台兼容性；不兼容时按独立规则流程另行恢复，不能让平台脚本覆盖 `/opt/aig/rule-data`。断电或 SIGKILL 后按备份中的阶段记录人工恢复，不能保证自动回滚已经发生。

## 独立规则更新如何继续

仍将每次规则脚本和配套规则包上传 `/opt/aig/rules/YYYY.MM.DD/`，由独立规则更新脚本处理校验、合并、备份、Web 重建和验收，不更换平台镜像。

平台升级后，只使用发布方验证支持当前平台的规则工具；旧工具硬编码 v1.1.0，不能在新版本上继续强行使用。管理工具修订与规则内容版本分开记录，只有实际应用规则候选且验收通过才改变规则部署记录。

首次解耦已经完成，不重复使用 `--migrate`。规则更新与平台升级分别执行、分别保留备份；不要同时运行。

## 当前尚不能直接使用的旧工具

- `upgrade-to-v1.1.0.sh`：只做 `/opt/aig-app` 的 v1.0.0 到 v1.1.0 首次迁移，不是通用平台升级工具。
- `package-intranet.ps1`：当前会将整个 data 打包；新纯平台发布需适配打包和镜像构建后再交付。
- `update-rules-2026.10.10-001.sh`：已用于 v1.1.0 契约布局，不能代表它支持所有未来平台版本。

本轮仅交付契约和操作文档，不生成示例 v1.2.0 包，也不修改服务器。下一次实际功能发布时，应按上述契约提供经过测试的两个平台文件，你上传后执行一条部署命令即可。
